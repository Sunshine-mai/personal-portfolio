# 个人工程作品集平台 V2 蓝图

## 结论

V2 不应继续做成“项目卡片集合”。它应成为一个可核验的个人工程档案馆：让招聘方在三分钟内看到成果，让技术面试官能顺着证据查看决策、系统边界和验证记录，让后续项目自然沉淀为可发布案例。

## 产品结构

### 公开区

1. 首页：能力主线、代表案例、当前工程方法和最近核验状态。
2. 项目档案：按独立项目、合作项目、原型方案筛选；每项显示验证等级而非虚假的完成度。
3. 项目详情：问题、角色边界、系统设计、关键决策、测试与交付证据、限制与下一步。
4. 工程方法：将设计先行、决策存证、全链路防御、验证和复盘做成可浏览的工作流。
5. 技术脉络：Java/Spring、Python/FastAPI、Vue、数据与部署之间的真实项目关联。
6. 学习复利：只展示经过整理的“问题 -> 处理方式 -> 可复用规则”，不公开私人反思日志。

### 管理区

1. 项目档案草稿和修订。
2. 证据登记：提交、测试报告、构建摘要、截图、外链核验、授权状态。
3. 审核门禁：授权、敏感信息、事实和链接状态必须全部通过。
4. 发布快照：公开 API 只读取不可变快照，编辑草稿不影响线上内容。
5. 审计与回滚：记录操作者、变更、发布和下线原因。

## 复利机制

每个新项目只新增一个 `project-audit/<slug>/` 审查包，内容为：

```text
inventory.md              项目范围和版本清单
contribution-boundary.md  个人贡献与授权边界
decision-records.md       决策、备选方案和代价
verification.md           单元、接口、浏览器、构建与部署证据
security-review.md        密钥、隐私、许可证和素材检查
portfolio-entry.md        可公开的案例正文
```

审查包通过后，管理端把 `portfolio-entry.md` 转为内容修订，把验证文件转为证据索引；作品集从此不需要重新翻项目源码拼材料。

## V2 内容模型

在现有 `Project` 和 `Revision` 之上，优先增加以下可独立维护的实体：

| 实体 | 必须字段 | 目的 |
|---|---|---|
| ProjectProfile | 项目性质、验证等级、最后核验日期、公开状态 | 让访客识别事实强度 |
| Contribution | 责任范围、团队成果、个人产出、授权等级 | 防止合作项目表述失真 |
| DecisionRecord | 背景、候选方案、选择、代价、关联修订 | 沉淀可面试的工程判断 |
| Evidence | 类型、摘要、来源、核验日期、公开等级 | 用证据支持声明 |
| VerificationRun | 类型、状态、执行时间、构建摘要 | 将“测试过”转为可追溯记录 |
| KnowledgeNode / Edge | 名称、关系、项目、学习状态 | 展示跨项目迁移，而非装饰图谱 |

## 信息与视觉原则

- 视觉主题沿用“编辑式工程档案馆”，采用纸张白、墨黑、矿物蓝、信号橙和验证绿，避免营销页和虚假科技感。
- 首页直接呈现项目成果与验证状态。大型字只用于项目名和结论，控制面板使用紧凑信息密度。
- 独立项目以完整案例呈现；合作项目使用明显的协作标签；原型使用 `PROTOTYPE` 标识并展示验收路径。
- 图谱必须有列表替代，移动端以筛选、时间线和案例详情为主，不压缩桌面图谱。
- 案例详情使用右侧抽屉或独立路径，支持链接分享，并保留键盘焦点和关闭交互。

## 技术实施建议

| 层 | 选型 | 原因 |
|---|---|---|
| 前端 | Vue 3 + Vite + Pinia + Vue Router | 延续现有已运行前端，适合档案、筛选、抽屉和管理工作流 |
| API | Java 17 + Spring Boot 3 + MyBatis-Plus | 复用已有 Java 项目的工程经验，适合模块化单体、输入校验和统一异常处理 |
| 数据库 | MySQL 8 | 与已有 Java 项目技术栈一致，便于本地、测试和生产环境统一 |
| 迁移 | Flyway | 以版本化 SQL 管理 MySQL schema，适合可追踪升级和部署回滚检查 |
| 认证 | Sa-Token，会话凭证优先 HttpOnly Cookie | 沿用已有 Java 项目的认证经验，降低浏览器端令牌暴露面 |
| 交付 | Git + Gitee、GitHub Actions 或 Gitee 流水线、Docker Compose | 发布前自动运行测试、构建和秘密扫描，产出可追溯快照 |

## 实施阶段

1. P1：完成本台账、V2 原型和四个项目审查包模板。
2. P2：确认原型后，使用 Java 后端建立兼容 API，并升级公开前端信息架构。
3. P3：补齐 MySQL/Flyway 数据模型、证据、贡献边界和验证记录的管理端页面。
4. P4：完成 AI Translator 和 AI Second Brain 的真实公开档案；大学新闻网等待授权；教学平台以原型案例发布。
5. P5：秘密/许可证扫描、后端测试隔离修复、浏览器验收、构建快照和人工发布确认。

## 当前阻断项

- 大学新闻网的公开授权、个人贡献范围和素材版权尚未确认。
- AI Translator 需要补齐正式 pytest、接口和浏览器测试证据，不能只使用历史验证脚本叙述。
- 现有作品集后端测试依赖本地持久数据库，需要隔离后才能作为发布门禁。
- V2 原型必须由站点所有者确认后才能迁入运行前端。
- Java 后端需要先完成 MySQL 连接、Flyway 基线和旧 Python API 的兼容映射。
